Conclusion first

The AirPods emulation in this firmware is much deeper than a fake name: it is a real Apple Accessory Protocol server, published over SDP on its own L2CAP PSM, with two Apple accessory HID services — one of which is a head-motion sensor service that only appears in the newer 377 build. It advertises itself over BLE as an AirPods Pro (gen 1), and it identifies over HFP with the battery-only feature bit.

Transparency is the opposite story. There is a live tuning interface — four ANC gain commands parsed straight off the AT channel — but no ANC or transparency filter data ships in any partition of any of the 24 images. The container format reserves page IDs for it and they are empty everywhere. So sound prompts and EQ are data edits; transparency is a firmware patch.

Everything below is read from h2sturbo 2506281656 (the newest 377-generation SL6801 image) and compared against h2sturbo 2409191721 and the other 22 catalog images. None of it has been observed on the H3Pro Max3, and nothing has been written to any device.

1. What the AAP surface actually contains

The firmware carries a pre-built SDP record blob at FIRM offset 0x55000–0x55930. Decoded, it publishes three records beyond the usual audio profiles.

The serial number is a single hardcoded string in flash, so every unit built on this image reports the same serial to iOS.

Two Apple accessory HID services

The identity blob embeds two full HID report descriptors. Decoded item by item, they are:

devmotion6 · 96-byte descriptor

Max report size 191 bytes.

  • Report 1 input: 64-bit field (usage page 0xFF15, usage 4) plus a 1456-bit (182-byte) vendor field (0xFF0C/0x0D) — the motion payload.
  • Report 2 input: 0xFF0C/0x0E.
  • Feature reports on the HID Sensors page (0x20): usages 0x030E, 0x031B, 0x031A.
  • Report 0xFF: a 224-byte vendor feature blob.

AVClient · 67-byte descriptor

Max report size 70 bytes.

  • Report 1 input: 552-bit (69-byte) field.
  • Reports 2–4 inputs: 8, 16 and 8 bits.
  • Feature 0x030E (32-bit) on reports 1 and 2.

HFP identity

Over the hands-free channel the firmware sends AT+XAPL=0042-0887-0100,2. Feature bit 1 is battery reporting; it is the only bit set. It also emits +APLSIRI:1 and handles AT+BVRA for voice assistant.

3. Transparency and ANC: what is actually tunable

A live gain interface exists

The incoming AT parser has a block of ANC commands. Each parses a decimal argument out of the string and posts a message with a fixed ID. Command +ANCAG= additionally parses a leading -, so the overall ANC gain is signed.

ANC AT commands accepted by the firmware
Command Message ID Argument Reads as
+ANCTEST=0xF40000012 digitsANC test mode select
+ANCFFG=0xF40000022 digitsFeed-forward mic gain
+ANCFBG=0xF40000032 digitsFeedback mic gain
+ANCAG=0xF4000004signedOverall ANC gain
+ANCDG=0xF4000005digitsDenoise / depth gain

Dispatch table at FIRM 0x96AA0–0x96AC4; handler code disassembled at 0x896744–0x8968B2 (Thumb-2, image base 0x7FFE14). Present in both builds. Whether the command channel accepts these without the keyed challenge/response is not verified.

But no filter data ships in any image

The container's parameter format reserves seven page IDs specifically for ANC, including three for talk-through — which is what this platform calls transparency:

  • 51 ANC_MIC_FORWARD, 52 ANC_MIC_FEEDBACK, 53 ANC_MIC_COMPENSATE
  • 54 ANC_MIC_TT_FORWARD, 55 ANC_MIC_TT_FEEDBACK, 56 ANC_MIC_TT_COMPENSATE
  • 57 ANC_ANHT

I parsed every EQ2P, SENC and SEN2 partition across all 24 catalog images and counted the page IDs present. Pages 51–57 appear zero times in zero images. What does ship:

The two EQ profiles are ANC-aware

The h2sturbo EQ2P holds the same five pages twice. The app's local store explains why: it keeps four scheme families — TYPE_EQ = 1, TYPE_ANC = 2, TYPE_ENC = 3, TYPE_ANC_2 = 4 — and EqScheme carries an isAnc flag. So the second profile is the ANC-mode EQ, and there is already a slot for a second ANC variant.

That is the one genuinely promising transparency lever that is data, not code: transparency mode gets its own output EQ profile, and the profile is an editable float table in a CRC-only partition. The two factory curves differ only slightly — the low-shelf sits at −2.0 dB in the first profile versus −1.8 dB at 130 Hz in the second, and the broadband trim differs (−4.80 dB versus −5.04 dB).

Open question, not settled: I have not proven which of the two EQ2P profiles the device binds to transparency rather than to ANC-on, nor that the H3Pro Max3 uses the same two-profile layout. Both need either a 377H3 image or a live read-back.

4. So — is there more to implement?

Already there

  • AAP server on its own PSM, with the real service and profile UUIDs
  • Apple vendor/product identity in SDP and BLE
  • Proximity-pairing pop-up with battery and lid-counter fields
  • Battery reporting over XAPL; Siri via BVRA
  • Ear detection (ear_detection_en, ear_type)
  • Head-motion accessory service with sensor-page feature reports (377 only)
  • Per-ear tap and long-press mapping in NV

Plausible gaps

  • Model spoof is stale. BLE says 0x0E20 (AirPods Pro gen 1) while SDP says product 0x2014. Two bytes decide the iOS pop-up and the feature set iOS offers.
  • XAPL features = 2. Only battery. Case-battery and the other feature bits are unset.
  • Shared serial number. One hardcoded string for every unit.
  • No evidence in strings or descriptors of conversation awareness, adaptive audio, or loud-sound reduction.
  • Noise-control from Control Center — I could not confirm an AAP listen-mode handler statically; the AAP opcodes are built in code, not in a table.

Practical summary for CFW. Prompts and EQ are data edits in CRC-only partitions — already proven repackable. The AirPods identity is a handful of literal bytes in flash, so it is a patch, not a rewrite. Transparency quality is the hard one: the filters are compiled into FIRM, the only exposed handles are four runtime gain commands, and the container format's ANC pages are unused everywhere. Improving it means either driving those gains live or patching code — and either way it needs a real 377H3 base image first.
